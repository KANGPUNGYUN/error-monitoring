# 에러 그룹화 정답셋 라벨링 가이드

> 이 문서는 연구 코어(SPEC 6장)의 1급 산출물이다. 라벨셋이 오염되면 실험 결론
> 전체가 무의미해지므로, 이 규약을 엄격히 따르고 재현 가능하게 기록한다.

## 1. 라벨의 정의 (좁게)

라벨링 대상은 **"근본 원인(root cause)"이 아니다.** 근본 원인은 stack/message만으로는
알 수 없다.

> **라벨 = "제공된 새니타이즈 텔레메트리만으로 판단했을 때, 두 에러가 같은
> actionable issue(같은 조치가 필요한 이슈)인가."**

- 판단 근거는 **라벨러에게 주어진 필드에 한정**한다(아래 3장). 추측한 외부 지식으로
  묶지 않는다.
- 같은 actionable issue = 개발자가 하나의 티켓으로 처리하고 한 번의 수정으로 해소할
  것으로 보이는 묶음.

## 2. 라벨 스킴

각 에러 이벤트에 `group_id`(정수)를 부여한다. 같은 issue = 같은 `group_id`.

추가 허용 라벨:
- `uncertain` — 같은 이슈인지 판단 불가. **정답셋에서 제외**(노이즈 오염 방지).
- `singleton` — 혼자인 이슈(정상. 강제로 묶지 않는다).

## 3. 라벨러에게 제공하는 필드 (그리고 금지)

제공(새니타이즈 후):
- exception type, 정규화된 message, top N app 스택 프레임(framework 프레임 제거본)
- route(정규화), status, environment, release, 최초/최근 발생 시각, 발생 수

**금지(누출 방지):**
- 알고리즘이 쓰는 것과 **동일한 단일 필드만 보고 기계적으로 묶지 말 것.**
  예: "top frame이 같으니 같은 그룹" → 규칙 엔진이 by construction 이긴다. 여러 신호를
  종합해 "같은 조치가 필요한가"로 판단한다.
- AI 엔진의 출력/제안을 라벨러에게 보여주지 않는다.
- 원시 request body/PII는 애초에 수집되지 않는다(SPEC 4.1).

## 4. 애매 케이스 규칙

- **같은 예외, 다른 원인** 의심 → route/release/시각 분포가 확연히 다르면 분리, 판단
  불가면 `uncertain`.
- **다른 예외, 같은 배포 버그** → 같은 release 이후 동시 급증 + 동일 조치 예상이면 병합
  가능하나 확신 없으면 `uncertain`.
- **framework wrapper 에러**(제네릭 메시지) → app 프레임/route 기준으로 판단, 불가면
  `uncertain`.
- **cascade 실패**(A 실패가 B를 유발) → 서로 다른 actionable issue면 분리.

원칙: **확신이 없으면 `uncertain`.** 억지 병합/분할이 지표를 망친다.

## 5. 샘플링 (층화)

랜덤 추출 금지 — 잦은 노이즈 에러에 과가중되고 경계 케이스가 과소대표된다.

- **exception type × route × 빈도 구간**으로 층화하여 추출.
- 희귀 에러·경계 케이스를 의도적으로 포함(각 층 최소 쿼터).
- 목표 규모: **500~1000 이벤트**(제외분 감안해 여유 있게 라벨).

## 6. 프로토콜 (연구 방어용)

1. **2인 독립 라벨.** 서로의 라벨을 보지 않고 각자 `group_id` 부여.
2. **IAA 측정·보고.** 쌍 단위 일치를 Cohen's κ(또는 그룹화용 일치도)로 계산.
   낮으면 가이드를 보강하고 재라벨.
3. **불일치 조정(adjudication).** 3자(또는 합의)로 최종 라벨 확정. 조정 로그 보관.
4. **dev/test 분리.** 정답셋을 dev(임계치·프롬프트 튜닝용)와 held-out test(최종 보고
   1회)로 나눈다. **test는 개발 중 절대 열어보지 않는다.**
5. **누출 금지.** 라벨을 프롬프트/임계치 튜닝에 쓴 뒤 같은 라벨로 평가하지 않는다
   (dev로 튜닝 → test로 평가).

## 7. 산출물

- `datasets/labels.dev.jsonl`, `datasets/labels.test.jsonl` — `{event_id, group_id}`
- `datasets/adjudication-log.md` — 불일치·최종결정 기록
- `reports/iaa.md` — κ 값과 해석
- 라벨 정의·애매 케이스 결정은 이 문서를 버전으로 인용(재현성)

## 8. 한계 명시 (논문/발표에 반드시)

- 우리는 root cause가 아니라 "관찰된 텔레메트리 기준 same actionable issue"를 측정한다.
- 새니타이즈로 일부 신호가 제거되어 상한이 존재한다.
- 단일/소수 프로젝트 데이터의 일반화 한계.
